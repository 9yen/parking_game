# 《一起停车吧》开发规范

- 适用版本：`v0.1` 起
- 目标：用尽量少的流程，持续交付可运行、可验证、可回退的版本。

## 1. 第一性原则

游戏开发的最小价值单位不是“写完一批代码”，而是玩家能完成一个有反馈的行为。因此每轮开发都必须形成可玩的纵向切片，并能回答三个问题：玩家做了什么、系统如何反馈、失败时是否安全。

优先级依次为：数据正确与不丢档、核心循环可理解、操作顺畅、视觉与声音打磨、远期扩展。尚未证明核心玩法前，不投入真实联机、交易市场和大规模内容生产。

## 2. 工作流

1. 在 `spec/` 写清本轮范围、非范围和可观察的验收条件。
2. 从 `main` 创建短期功能分支，提交保持单一主题。
3. 先实现不依赖界面的领域规则及测试，再连接场景和表现。
4. 运行自动测试、Godot 无头启动检查和人工冒烟测试。
5. 验收通过后合并；失败版本不得标记为可发布构建。

小团队可以由同一人承担产品、开发和测试角色，但必须在不同阶段分别检查，避免“代码能运行”被误认为“玩家需求已完成”。

## 3. 完成定义

一项功能只有同时满足以下条件才算完成：

- 行为与当前规格一致，异常路径有明确反馈。
- 核心规则有自动测试，测试不依赖真实等待。
- Godot 无脚本解析、资源缺失和启动错误。
- 存档字段有默认值和版本号，重复操作不会重复发奖。
- 玩家可见文本经过本地化层，至少提供简体中文和英语。
- 新增产品行为已同步规格；新增项目文档已加入索引。
- 没有把密钥、构建产物、个人路径或用户数据提交到仓库。

## 4. 质量门槛

- P0：丢档、重复发钱、无法启动、安全或隐私问题。必须立即阻止发布。
- P1：核心循环中断、车辆状态错误、主要操作无反馈。修复后才可验收。
- P2：次要界面、文案或视觉问题。记录后可在同一里程碑修复。
- P3：纯优化建议。进入待办，不阻塞当前版本。

任何经济与计时变更都必须覆盖边界值：零时长、恰好 8 小时、超过 8 小时、重复召回和损坏存档。

## 5. 发布节奏

- `0.1.x`：内部可玩原型，验证核心循环。
- `0.2.x`：外部试玩，验证教学、节奏和价值感。
- `0.x` 后续：内容与平台能力逐步加入。
- `1.0`：只在首发范围、稳定性、商店素材和支持预案都完成后发布。
